# 스마트예매 속도 측정

Node.js 22 이상으로 실행한다. 별도 패키지 설치는 없다. **후보 생성 → 첫 상태 조회 → 이번 요청 취소**를 반복한다. 서버 코드는 바꾸지 않는다.

## 준비

1. 테스트 DB를 사용하는 서버를 실행한다. 실제 선점·대기를 만들므로 운영 DB에서 실행하지 않는다.
2. 성인 테스트 계정을 준비하고 선호 극장·좌석을 설정한다. 해당 극장에 측정 날짜·시간의 상영 회차가 있어야 한다.
3. 동시 사용자 수만큼 서로 다른 계정을 사용한다. 모든 계정의 선호 극장·좌석 순서를 같게 맞추고 기존 대기·선점은 비워 둔다.
4. `.local/smart-benchmark-users.json`을 아래 형태로 만든다. `.local`은 Git에서 제외된다.

```json
[
  { "loginId": "bench01", "password": "테스트 계정 비밀번호" },
  { "loginId": "bench02", "password": "테스트 계정 비밀번호" }
]
```

`scripts/smart-booking-benchmark/example.json`의 `movieId`와 시간을 실제 데이터에 맞춘다. 복사해서 사용하면 `usersFile`은 **설정 파일 위치 기준 경로**다.

- `viewingDate`: `tomorrow`는 실행 시 한국 시간 기준 내일로 고정한다. 날짜를 직접 지정해도 된다.
- `ranges`: 1시간·4시간·하루 예시. 종료가 시작보다 이르면 다음 날 종료다. `06:00 → 05:59`는 23시간 59분이다.
- `concurrency`: 처음에는 `[1]`. 이후 `[1, 5, 10]`으로 늘린다. 가장 큰 값만큼 계정이 필요하다.
- `rounds × iterations × concurrency`: 범위·동시 사용자 조합별 측정 표본 수. 기본은 각 범위 30개다. p99 비교에는 더 많은 표본이 필요하다.
- `warmupIterations`: 각 조합의 사전 실행 횟수. 결과 통계에서 제외하지만 DB 기록은 남는다.
- `label`: `before-cache-off`, `after-cache-off`, `after-cache-on`처럼 실험 이름을 적는다. 캐시를 켜거나 끄는 설정은 아니다.

## 실행

프로젝트 루트에서 계획을 먼저 확인한다. 이 명령은 서버에 요청하지 않는다.

```powershell
node scripts/smart-booking-benchmark/run.mjs scripts/smart-booking-benchmark/example.json
```

실제 측정:

```powershell
node scripts/smart-booking-benchmark/run.mjs scripts/smart-booking-benchmark/example.json --run
```

실행 순서는 라운드마다 회전한다. 각 반복은 사용자별 생성·조회·취소를 마친 뒤 다음 반복으로 넘어간다. 로그인과 취소는 지연 통계에서 제외한다. 실패가 있으면 종료 코드 1을 반환한다.

## 결과

`benchmark-results/smart-실행시각-고유번호/`에 저장한다.

| 파일 | 내용 |
|---|---|
| `report.md` | 범위·동시 사용자별 성공/실패, 생성·조회 p95, API 합계 p50/p95/p99 |
| `summary.json` | 평균·최댓값·실패 요청 시간·선점/대기 후보 수 등 비교용 통계 |
| `samples.jsonl` | 요청별 시간·HTTP 상태·후보 상태. 워밍업 여부 포함 |
| `manifest.json` | 서버·날짜·범위·사용자 ID·선호 조건 |
| `journal/` | 이번 실행의 요청 키·후보 ID·정리 여부. 강제 종료 복구에 사용 |

비밀번호·토큰·응답 원문은 결과에 저장하지 않는다. 실패 응답을 성공 시간에 섞지 않는다. 후보가 없다는 409도 실패로 집계하므로 **먼저 모든 범위에서 정상 추천이 되는지 확인**한다.

## 중단·복구

Ctrl+C 한 번은 진행 중인 요청을 정리한 뒤 종료한다. 강제 종료·통신 장애에 대비해 생성 전에 요청을 기록한다. 정리 실패 시 추가 부하를 멈춘다.

```powershell
node scripts/smart-booking-benchmark/run.mjs scripts/smart-booking-benchmark/example.json --recover=benchmark-results/smart-실제결과폴더
```

복구는 원래 실행의 서버 주소·날짜를 사용한다. 같은 테스트 계정 파일을 사용하고, DB를 교체하기 전에 실행한다. 결과를 못 받은 생성은 **같은 멱등성 키와 요청**으로 다시 확인한 뒤 취소한다. 최초 요청이 서버에 도달하지 않았다면 복구 과정에서 생성 후 취소될 수 있다. 이번 실행에서 확인한 후보만 취소하며 다른 신청은 건드리지 않는다.

## 공정하게 비교하는 법

- 현재 코드 / 구조 개선+Redis OFF / 동일 구조+Redis ON을 동일 서버 자원·DB 스냅샷·계정·범위로 비교한다. 커밋과 캐시 설정도 따로 기록한다.
- 자동 취소는 활성 선점·대기를 해제한다. 취소 내역·발급 순번·멱등성 기록까지 삭제하지는 않는다. 같은 상태로 비교하려면 테스트 DB 스냅샷을 복원한다.
- 회차가 1개인 1시간 범위와 1개인 하루 범위는 탐색량이 비슷하다. 실제 포함 회차 수를 함께 기록한다. 이 스크립트는 내부 조회 회차 수를 추측하지 않는다.
- 빈 좌석이 많은 상태와 매진 상태는 다른 실험이다. `holdingCandidates`·`waitingCandidates`가 크게 달라지면 시간을 그대로 비교하지 않는다.
- 동시 테스트에는 생성·취소가 섞이고 좌석 경쟁도 발생한다. 단일 요청 비용은 동시 1, 경쟁 시 지연은 동시 여러 명으로 구분한다.
- 합계는 **두 API의 응답 본문 수신까지 걸린 시간의 합**이다. 브라우저 렌더링, 로그인, 파일 기록, 정리는 제외한다. 화면 표시까지의 실제 시간은 브라우저에서 따로 측정한다.
- 이 실험은 고정 동시 사용자 반복 방식이다. 최대 RPS·정확한 동시 클릭·SQL 횟수·잠금 대기·CPU 시간을 측정하는 도구는 아니다. 서버 병목 원인은 별도 계측으로 확인한다.

## 스크립트 자체 검증

```powershell
node --test scripts/smart-booking-benchmark/run.test.mjs
```

실제 서버 대신 임시 HTTP 서버를 사용한다. 성공·실패 분리, 다중 계정, 기존 신청 보호, 응답 유실 복구, 조회 실패 후 정리, 정리 실패 시 중단을 확인한다.
