# 사이트 접속 대기실

사이트 접속 시 대기실을 먼저 거친다. 입장 전에는 AuthProvider와 사이트 화면을 마운트하지 않아 로그인 정보·영화·티켓 조회가 시작되지 않는다. 입장이 허용되면 원래 URL에서 사이트를 이용한다. 기존 취소표 배정 대기열과는 독립된 기능이다.

## 배포 및 설정

Docker Compose는 `ADMISSION_ENABLED=true`로 활성화한다. 로컬 실행과 기존 DB 부하 벤치마크의 기본값은 false다. 로컬에서 확인하려면 백엔드를 `ADMISSION_ENABLED=true`, Redis 실행 상태로 시작한다. 프런트는 기존 개발 서버를 사용한다. HTTPS 배포는 HttpOnly·Secure·SameSite=Lax 쿠키를 사용하며 프런트와 API가 같은 사이트에 있어야 한다.

| 환경변수 | 기본값 | 의미 |
|---|---:|---|
| ADMISSION_CAPACITY | 100 | 동시에 입장 상태를 유지할 인원 |
| ADMISSION_BATCH_SIZE | 10 | 초당 최대 신규 입장 인원 |
| ADMISSION_ACTIVE_SECONDS | 600 | 마지막 허용 API 요청부터 입장 유효시간 |
| ADMISSION_WAIT_SECONDS | 90 | 대기 상태 확인이 끊겼을 때 만료 시간 |
| ADMISSION_MAX_WAITING | 20000 | 최대 대기 인원, 초과 시 등록 재시도 |
| ADMISSION_REDIS_HOST | 기존 Redis 주소 | 배포에서는 별도 admission-redis |

위 수치는 초기 보호 설정이며 5천 명 처리 용량을 보장하는 측정값이 아니다. 실제 서버에서 유입·입장 후 행동을 함께 부하 측정해 조정한다. 변경 시 백엔드 재시작이 필요하다.

## 처리 및 장애 정책

- Redis의 증가 순번으로 정렬한다. 같은 쿠키의 재등록은 순서를 바꾸지 않는다. 브라우저 탭은 같은 입장권을 공유한다.
- 여유가 있고 초당 입장 한도 내라면 바로 입장한다. 대기자가 이미 있으면 먼저 온 사람부터 처리한다. 평상시에도 무조건 몇 초씩 기다리게 하지 않는다.
- 기다리는 사용자는 5~10초 간격에 무작위 지연을 더해 확인한다. 최대 대기 초과는 15초 후 재시도한다. 예상 대기시간을 임의로 표시하지 않는다.
- 스케줄러가 정원을 확인하고 입장 상태 등록 후 대기 상태를 제거한다. Lua와 Redis 공통 시각, 전체 인스턴스의 공통 승급 간격으로 중복 승급과 정원 초과를 방지한다.
- 실제 API 사용은 입장 만료를 연장하지만 대기실 상태 확인만으로는 연장하지 않는다. 명시적 대기 취소는 즉시 정리하며 연결 종료는 만료로 정리한다.
- 입장권은 로그인 인증을 대체하지 않는다. 사이트 API·OAuth 요청을 인증보다 앞에서 검사한다. readiness와 CORS preflight, 정적 프런트 파일은 통과한다.
- Redis 장애 시 503으로 닫고 자동 재시도 화면을 보인다. 전체 입장 허용으로 전환하지 않는다. 캐시 ON/OFF 스위치와도 독립적이다.
- 배포 대기열 Redis는 AOF와 noeviction을 사용한다. Redis 재생성으로 데이터가 없어지면 다시 대기 등록하며, 현재 구성은 Redis 단일 노드이므로 무중단 고가용성을 보장하지 않는다.
- Nginx에서 대기실 요청은 IP당 5회/초, 일반 API는 30회/초(각각 burst 15/60)를 제한한다. 공유 NAT 사용자 영향을 관찰해 조정한다. 봇·DDoS 방어 전체를 대체하지 않는다.

## 운영 범위

정적 대기 화면은 프런트에서 제공하고 입장 검사는 백엔드의 가장 앞단 필터에서 수행한다. DB 유입은 줄이지만 HTTP 연결·TLS·백엔드 입장 검사 자체의 비용은 남는다. 네트워크 포화까지 막으려면 CDN/WAF 및 독립 게이트웨이 계층을 추가해야 한다. 대기열 Redis 포트와 backend 포트를 외부에 직접 공개하지 않는다.

입장 만료 시 요청을 자동 재전송하지 않는다. 예매·결제 요청의 중복 실행을 피하고, 다시 입장한 후 기존 예매 복구 경로를 사용한다. 알림 SSE 연결은 60초 수명으로 제한해 재접속 시 입장권과 인증을 다시 검사한다. 이미 성립한 연결까지 즉시 끊는 방식은 아니다.

배포 smoke 검사는 일반 사용자와 동일하게 입장한 후 API를 검사하고 마지막에 입장권을 반환한다. readiness에는 우회용 비밀 헤더나 별도 사용자 예외를 넣지 않는다.
