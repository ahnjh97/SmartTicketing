# 가까운 극장 공간 검색

`/api/theaters/nearby`는 MySQL에서 거리를 계산하고 가까운 활성 극장을 최대 12개 반환한다. 애플리케이션으로 전체 극장 목록을 가져오지 않는다. 서울에 한정하지 않으며 결과가 12개보다 적으면 검색 범위를 넓힌다.

## 공간 데이터와 동기화

- 원본 좌표는 `theaters.latitude`, `theaters.longitude`이다.
- `theater_locations`에는 유효한 좌표가 있는 극장의 ID와 `POINT(경도, 위도)`를 저장한다. 좌표가 없거나 범위를 벗어나면 검색용 행을 만들지 않는다.
- `location`은 `POINT NOT NULL SRID 0`이며 `idx_theater_locations_point` 공간 인덱스를 사용한다. SRID 0의 평면 경계 상자로 후보를 검색하고, 최종 거리는 구면 거리 함수로 계산한다.
- 극장 INSERT/UPDATE 트리거가 동일 트랜잭션에서 공간 좌표를 동기화한다. 좌표 제거도 반영하고, 극장 삭제 시 외래 키의 `ON DELETE CASCADE`로 공간 데이터도 삭제한다. 비활성 극장은 조회 조건에서 제외한다.
- 애플리케이션 기동 시 Hibernate의 극장 테이블 준비 이후 `TheaterSpatialSchema`가 공간 테이블·트리거를 생성하고 기존 좌표를 반영한다. 반복 실행할 수 있으며 DB 이름별 잠금으로 여러 인스턴스의 초기화를 직렬화한다.

현재 배포 설정의 DB 계정은 스키마를 생성할 수 있다. 별도 계정으로 운영할 경우 공간 스키마 초기화에는 CREATE·TRIGGER 및 데이터 갱신 권한이 필요하다. 바이너리 로그를 사용하는 서버의 트리거 생성 권한 정책도 적용된다. 실제 운영 데이터에 반영되는 시점은 변경된 백엔드의 다음 기동이다.

## 검색 순서

1. 사용자 좌표 주변 2km 원을 포함하는 경계 상자를 계산한다.
2. `MBRIntersects`와 공간 인덱스로 상자 안의 후보를 조회한다.
3. MySQL의 `ST_Distance_Sphere`로 실제 거리를 계산하고, 원 내부 결과만 거리·이름·ID 순으로 정렬해 12개로 제한한다.
4. 12개가 안 되면 반경을 두 배로 넓힌다. 최종적으로 지구 전체를 포함하는 범위까지 검색하며, 극장 자체가 12개 미만이면 있는 결과만 반환한다.

상자 안에 12개가 있다는 이유만으로 종료하지 않는다. 원 내부에 12개가 있어야 범위 밖에 더 가까운 극장이 없다는 것을 보장할 수 있다. 극점이나 날짜 변경선을 걸치는 상자는 경도 전체를 포함하도록 넓히고 실제 거리 조건으로 거른다.

구면 거리의 지구 반지름은 기존 계산과 같은 6,371,000m이다. DB에서는 반올림 전 거리로 정렬하며 API의 거리 값은 정수 미터로 반올림한다. 도보·대중교통 경로 조회는 이 후보 목록을 사용하며, 실제 소요 시간은 기존 외부 지도 API에서 가져온다. 도보 후보의 기존 2km 제한도 유지한다.

## 확인 범위

MySQL 통합 테스트는 전체 거리 정렬 결과와의 일치, 전국으로의 범위 확장, 극장 수 부족, 좌표 변경·제거·삭제, 날짜 변경선·극점, 기존 데이터 반영을 확인한다. `EXPLAIN FORMAT=JSON`으로 공간 인덱스의 `range` 접근도 확인한다. 이 결과는 정확성과 인덱스 적용 여부에 대한 확인이며 부하 상황의 응답 시간 개선율은 별도 측정 대상이다.

공간 인덱스 동작은 [MySQL 공간 인덱스 문서](https://dev.mysql.com/doc/refman/8.4/en/using-spatial-indexes.html)를 참고한다.
