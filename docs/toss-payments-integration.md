## 2. Recommended integration shape

Keep MOCK and Toss as separate payment paths initially. Do not simply change `MOCK` to `TOSS` in the existing request: Toss requires a provider checkout/authorization step and a server-side confirmation call.

1. The authenticated backend creates/returns a unique Toss `orderId` for the current user's pending reservation. The server derives the amount from the stored reservation, never from a browser-supplied price.
2. The React client loads the Toss Payments SDK v2 using the **client key** and opens the checkout with that `orderId`, server-calculated amount, and success/failure URLs.
3. On redirect to success URL, the browser sends `paymentKey`, `orderId`, and `amount` to an authenticated backend confirmation endpoint.
4. The backend verifies ownership, pending status, hold expiry, expected amount, and order ID against persisted data, then calls Toss's payment confirmation API using the **secret key**.
5. Only after Toss returns a successful confirmation should SmartTicketing mark the payment successful, confirm the reservation/seats, issue the ticket, complete the booking group/queue, and append the existing outbox event.
6. Persist the provider's `paymentKey` and `orderId` with a uniqueness constraint. Make confirmation idempotent so refreshes/retries cannot issue duplicate tickets or charge/confirm the same reservation twice.
7. On provider confirmation failure, leave the reservation pending if the hold remains valid, surface a safe error, and permit a retry. Never trust the success URL alone.
8. Cancellation after a real Toss payment must call the Toss cancel/refund API before local state is marked cancelled. The current mock cancellation path must not be reused for a real payment without this step.

- `src/main/resources/application.properties`: bind environment variables for the Toss client key and secret key. Never put real key values in source control.
- Add tests for amount tampering, order ID mismatch, wrong user, expired hold, duplicate confirmation, Toss rejection/timeout, repeated redirect, ticket uniqueness, cancellation/refund failure, and existing mock flow regression.

## 4. Get test API keys (Korean Developer Center)

1. Open the [Toss Payments Developer Center](https://developers.tosspayments.com/) and sign up/sign in.
2. Open the developer/test store available to your account. Before completing a payment-service contract, you can use documentation test keys; signing in lets you view your own test-store activity and API logs.
3. Open **API 키** (API Keys) and make sure the environment is **테스트** (Test), not Live.
4. For the recommended current **주문서형/결제창형 결제 SDK v2** integration, use the matching **결제 연동 키** (payment integration keys): a client key and its paired secret key. Test keys begin with `test_`; client keys are public to the browser, secret keys are server-only.
5. Copy the client key to the local frontend environment and the secret key to the backend environment. Do not commit either actual value. Do not mix keys from different stores or environments.
6. Test payments are simulated and do not debit real funds. Verify attempts and API logs in the Developer Center.
7. Live payments require the relevant merchant/contract setup and live keys; do not switch production to live keys until the full checklist and refund path have been tested.

## 5. Local environment variables

Add these to the untracked local `.env` / shell environment after the integration code is implemented:

```dotenv
# Public key: frontend may read this via Vite's VITE_ prefix
VITE_TOSS_CLIENT_KEY=test_gck_REPLACE_WITH_YOUR_TEST_CLIENT_KEY

# Private key: backend only; never use VITE_ prefix
TOSS_SECRET_KEY=test_gsk_REPLACE_WITH_YOUR_TEST_SECRET_KEY
```

The key prefixes above describe the recommended v2 payment-integration key type; use the exact pair shown in your own Developer Center. Do not copy the placeholder strings as actual credentials.

For Docker/production, pass `TOSS_SECRET_KEY` only to the backend container through the server's secret environment configuration. Pass the client key to the frontend build environment as needed. Since Vite variables are embedded into the built JavaScript, only the client key may use a `VITE_` prefix.

## 7. Important implementation warning

The current booking service intentionally couples seat locking, reservation confirmation, ticket issuance, queue completion, and outbox publication. A provider network call should not be blindly inserted inside the long-running database transaction. The implementation should use a carefully designed two-stage orchestration/idempotency strategy, while retaining the existing seat-lock and state validation rules. This is why the branch starts with a reviewable integration plan rather than changing the existing mock payment path unsafely.
