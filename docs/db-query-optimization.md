# 영화·극장·상영시간 조회 최적화

영화·극장 목록과 상영시간·좌석도 조회의 데이터 로딩 및 인덱스 변경을 설명한다.

## 변경

- 영화 목록은 목록 응답 필드만 조회한다. 상세 설명·출연진 등의 데이터와 관리 엔티티 생성을 제외한다.
- 극장 목록도 응답 필드만 조회하고, 빈 검색어에는 `name LIKE '%%' OR address LIKE '%%'` 조건을 붙이지 않는다. 검색어가 있으면 기존 부분 일치 및 와일드카드 이스케이프 규칙을 유지한다.
- 상영시간 목록·좌석도는 좌석 표시와 연속 좌석 계산에 필요한 스칼라 값만 조회한다. `Seat`·`ShowtimeSeat` 관리 엔티티 및 예약·선점 정보는 읽지 않는다.
- 여러 회차의 재고는 회차 ID 100개씩 조회한다. 전체 회차를 생략하지 않으며, 각 좌석의 정렬·활성 여부·상영관 일치 조건을 유지한다. 연속 좌석과 분할 인원 계산에는 배치 정보가 필요하므로 단순 잔여 좌석 수 집계로 대체하지 않는다.

## 추가 인덱스

| 테이블 | 인덱스 컬럼 | 대상 |
|---|---|---|
| movies | is_active, id | 활성 영화 목록과 개수 |
| theaters | is_active, name, id | 검색어 없는 극장 목록 정렬 |
| theaters | is_active, brand, name, id | 브랜드 필터와 목록 정렬 |
| showtimes | movie_id, status, start_time | 영화·상영 상태·시간 범위 조회 |
| waiting_queues | showtime_id, status, seat_zone, zone_queue_number | 회차·대기 상태·구역별 조회 및 집계 |

기존 인덱스는 유지한다. 현재 앱은 Hibernate `ddl-auto=update`로 새 인덱스를 추가하므로, 다음 기동 시 기존 DB에도 생성 대상이 된다. 데이터가 큰 운영 DB에서는 인덱스 생성 시간과 쓰기 영향을 고려해 적용해야 한다. `validate`를 사용하는 환경에서는 별도 스키마 적용이 필요하다.

구역 대기 순번의 기존 번호 호환 처리(`coalesce`)와 극장 부분 일치 검색(`%검색어%`)은 남아 있다. 새 인덱스가 이 조건을 모두 범위 탐색으로 바꾸지는 않는다. 실제 인덱스 선택은 데이터 분포와 실행 계획으로 확인한다.

## 성능 비교 조건

공통 벤치마크와 동일 데이터로 기준/개선 커밋을 실행한다. Redis와 접속 대기실 설정, 메인 L1 캐시 설정도 동일하게 고정한다. DB 효과를 분리할 때는 Redis를 끄고, 대기실을 꺼 입장 제한이 측정을 대신하지 않도록 한다.

- SQL 수뿐 아니라 조회 컬럼, ORM 엔티티 로드 수, 실제 실행 계획과 p95를 함께 확인한다. 이번 좌석 개선은 SQL 수 감소가 아니라 불필요한 데이터와 관리 엔티티 감소가 핵심이다.
- 100개를 넘는 회차에서는 배치 수만큼 SQL이 늘어나는 대신 한 번의 IN 조건과 중간 조회 결과 크기를 제한한다. 최종 응답 전체 크기를 제한하는 페이지네이션은 아니다.
- 조회 오류·누락·정렬·좌석 계산의 회귀 테스트와 성능 부하 측정은 구분한다. 아직 속도 개선율은 측정하지 않았다.
